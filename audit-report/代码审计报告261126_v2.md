### 一、P0：实盘资金安全与核心交易阻断级问题（3 项 · 实盘前必改）

#### V2-T1. `_check_exits` 未校验均线追踪 K 线的收盘时间，激活追踪瞬间会读「开仓前的旧 15m K 线」误平盈利单
- **位置**：[trader.py](file:///Users/tony/Documents/playground/freedom/ma-trader/backend/trader.py#L1009-L1082)、[strategy.py](file:///Users/tony/Documents/playground/freedom/ma-trader/backend/strategy.py#L615-L632)
- **触发机理与复现路径**：
  1. 在新方案 A（`balanced`）与方案 B（`breakout`）中，大周期门禁 `check_htf_mode_scalars` 只要求 `HTF_MA7 > MA25 > MA60` 及 `close > MA200`，**允许上一根 `15m` K 线因正常回踩收盘在 `15m MA25` 下方**。
  2. 假设 `09:45~10:00` 的 `15m` K 线回踩收于 `15m MA25` 下方，但均线仍多头排列；`10:03` 小周期 `1m` 确认做多开仓；`10:09`（仍在 `10:00~10:15` 未收盘的 `15m` K 线内）价格快速拉升触及 `+1.0R`，`trader.py:1015` 将 `trailing_active` 设为 `True`。
  3. **紧接着同一轮 `_check_exits` 第 1049 行**立即进入 `if trailing_active:`，拉取 `15m` K 线并执行 `eval_df = df.iloc[:-1]`——此时 `eval_df.iloc[-1]` 拿到的是**开仓前早已收盘的 `09:45~10:00` 旧 K 线**！`strategy.check_exit()` 发现该旧 K 线 `close < ma25`，**当场触发 `htf_ma25_trailing` 把刚起飞的盈利多单误平出局**。
  4. 代码佐证：`trader.py:1071-1076` 构造了 `position_dict = {"direction": ..., "open_time": open_time, ...}` 传给 `strategy.check_exit()`，但 `strategy.py:615` **完全没有读取和判断 `open_time`**！而回测引擎 `backtester.py:366` 有 `htf_idx != last_seen_htf_idx` 门控（必须等**下一根新 15m K 线收盘**才检查），导致实盘/模拟盘与回测产生严重背离。
- **修复建议**：
  - 在 `pos` 中记录激活追踪的时间戳 `trailing_activated_at = datetime.now(timezone.utc)`；
  - 在 `_check_exits` 中校验 `eval_df.iloc[-1]["timestamp"] + rail_tf_duration > max(open_time, trailing_activated_at)`（即该根追踪周期 K 线必须是在**激活追踪之后才正式收盘**的 K 线），满足后才执行 `trail_ma_val` 移损与 `check_exit` 破线平仓。

#### V2-T2. 实盘移动止损失败时仍覆写本地 `stop_loss` 导致永久失步 + 缺少币安 `-2021` 盘口价保护
- **位置**：[trader.py](file:///Users/tony/Documents/playground/freedom/ma-trader/backend/trader.py#L863-L884)、[trader.py](file:///Users/tony/Documents/playground/freedom/ma-trader/backend/trader.py#L1057-L1093)、[executor.py](file:///Users/tony/Documents/playground/freedom/ma-trader/backend/executor.py#L277-L310)
- **两处联动缺陷**：
  1. **失败静默失步（最危险）**：`_sync_exchange_sl`（`trader.py:880-883`）代码如下：
     ```python
     if isinstance(res, dict) and res.get("updated"):
         pos["sl_order_id"] = res.get("sl_order_id")
         return float(res.get("stop_loss") or new_sl)
     return new_sl  # ❌ Bug：当 updated=False（挂单失败/网络超时/被拒）时，依然返回了 new_sl！
     ```
     一旦 `update_stop_loss` 失败，`trader.py:1088-1091` 仍把内存 `pos["stop_loss"]` 和 SQLite 数据库更新为 `new_sl`。到了 15 秒后的下一轮循环，`prev_sl` 已经等于 `new_sl`，`moved_enough`（`abs(stop_loss - prev_sl) / prev_sl >= 0.0002`）恒为 `False`，**系统永远不会再重试向币安更新止损单**！若此后服务重启或断网，界面显示“已移至保本止损”，但币安交易所上实际只挂着最初的远端止损单。
  2. **缺少实时价格边界保护，易触发币安 `-2021 Order would immediately trigger`**：`trader.py:1061` 按上一根已收盘均线算 `new_sl = max(stop_loss, trail_ma_val * 0.999)` 时，未校验当前实时价格 `price`。若盘中价格正回踩在 `trail_ma_val * 0.9985`（尚未跌破原止损，但已低于 `new_sl`），向币安提交做多 `STOP_MARKET (stopPrice >= 当前价)` 必报 `-2021` 拒单，进而直接触发上述第 1 点的永久失步！
- **修复建议**：
  1. `_sync_exchange_sl` 在 `res.get("updated")` 为 `False` 时必须返回 **`pos["stop_loss"]`（原止损价）**，保留差值以便下一轮自动重试，并向系统日志广播告警；
  2. 计算 `new_sl` 时增加实时价安全间距夹紧：做多限制 `new_sl <= price * 0.999`、做空限制 `new_sl >= price * 1.001`；若价格已跌破目标 `new_sl` 则直接触发平仓或等待下一轮，避免无意义触发 `-2021`。
